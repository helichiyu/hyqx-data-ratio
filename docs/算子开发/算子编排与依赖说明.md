# 算子编排与依赖说明

> 日期：2026-11-19
> 目的：说明平台任务与当前 14 个算子的对应关系、`map.json` 里 `dependsOn` 的真实含义，以及为什么会出现“算子之间依赖很多”的情况。

---

## 1. 结论先行

1. 平台不存在“一个任务调一个算子”的硬规则；一个业务任务对应一条固定的**短链路**，通常是 2 到 3 个算子。
2. 平台页面上的业务任务一共 5 类：数据打标、语料画像、配方仿真、配比生产、配比分析。
3. 算子是**能力单元**，不是页面任务；平台当前接入 14 个，均已进入业务链路。
4. `map.json` 的 `dependsOn` 记录的是**上游数据产物**，不是“任务必须先跑哪个算子”，平台也不读它来调度。大部分上游还是可选输入。
5. 真正的问题不是算子太多，而是 `dependsOn` 没有区分“必需输入”和“可选输入”，又和任务链混在一起看，才显得复杂。

---

## 2. 平台任务与算子链路

| 业务任务 | 实际调用链 | 说明 |
| --- | --- | --- |
| 数据打标 | OP-01 → OP-02 → OP-05 | OP-01 解析、OP-02 标准化、OP-05 打标 |
| 语料画像 basic | OP-01 → OP-02 → OP-06 → OP-08 | 规模、来源、领域覆盖；OP-06 失败则任务失败，不降级 |
| 语料画像 language | OP-01 → OP-02 → OP-09 | 语言、地域、时效 |
| 语料画像 text | OP-01 → OP-02 → OP-10 | 文本属性、任务适配 |
| 语料画像 speech | OP-01 → OP-02 → OP-11 | 语音质量、声学属性 |
| 语料画像 visual | OP-01 → OP-02 → OP-12 | 图像/视频属性 |
| 语料画像 knowledge | OP-01 → OP-02 → OP-13 | 知识覆盖、热点、风格 |
| 语料画像 quality | OP-01 → OP-02 → OP-14 | 质量、一致性、难度 |
| 配方仿真 | OP-16 | 平台自己生成 `plan.json` 后调用 |
| 配比生产 | OP-17 | 复用已完成打标的 OP-02 记录与 OP-05 标签 |
| 配比分析（报告） | OP-19 | 聚合 OP-17 产物与画像产物 |
| 配比分析（九维/比例） | OP-16 | 复用生产任务的 `plan_output_dir` |

为什么打标和画像都要先过 OP-01、OP-02：OP-01 负责把混合文件拆成文本、图像、音频、视频并解析；OP-02 负责统一成标准容器、分区、manifest、元数据和去重。后面的打标、7 类画像、配比生产都读同一份标准产物，如果每个算子各自解析一遍，口径会不一致，也无法复用。

## 4. dependsOn 的现行口径

它表达“算子的输入可以来自哪个算子的产物”，不是运行时调度图。平台每个业务任务在代码里写死一条短链，按顺序调用 `/{operatorId}/predict`，把上一步的 `outputDir` 传给下一步。

2026-11-19 已把保留算子的登记改为实际消费关系：

| 算子 | dependsOn | 说明 |
| --- | --- | --- |
| OP-01 | 无 | 入口 |
| OP-02 | OP-01 | 必需 |
| OP-05 | OP-02 | 必需 |
| OP-06 | OP-02 | 只读 OP-02 记录，不依赖 OP-05 |
| OP-08 | OP-02、OP-06 | OP-02 必需；OP-06 提供领域覆盖 |
| OP-09 | OP-02 | 读标准记录 |
| OP-10 | OP-02、OP-06 | OP-06 领域标签可选 |
| OP-11 | OP-02 | 读标准记录与媒体路径 |
| OP-12 | OP-02 | 读标准记录与媒体路径 |
| OP-13 | OP-02 | 必需 |
| OP-14 | OP-02、OP-05 | OP-05 标签可选 |
| OP-16 | 无 | 消费平台生成的 plan.json |
| OP-17 | OP-02、OP-05 | plan + 标准记录 + 标签 |
| OP-19 | OP-08 至 OP-17 | 聚合器，传哪些聚合哪些 |

## 5. 平台任务链

平台任务链单独维护，不写进算子依赖：

1. 打标：OP-01 → OP-02 → OP-05；
2. 画像 basic：OP-01 → OP-02 → OP-06 → OP-08；
3. 其他画像：OP-01 → OP-02 → 对应画像算子；
4. 生产：OP-17；
5. 分析：OP-19 或 OP-16。

`map.json` 仍只保留一个 `dependsOn` 字段，表达主要上游；可选输入在算子 README 的参数表中说明。平台调度不读取该字段，改动不影响运行。

---

## 6. 与分类树、OP-06 的关系

领域覆盖的现行链路为：

```text
OP-01（解析） → OP-02（标准化） → OP-06（领域/能力标签） → OP-08（画像，传 domain_labels_path）
```

OP-06 不是 OP-05 的下游，OP-08 也不消费 OP-05；map.json 的登记已按此修正，避免编排方误以为必须先跑打标。
