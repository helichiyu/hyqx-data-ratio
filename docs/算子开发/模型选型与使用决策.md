# 模型选型与使用决策（数据配比中心算子）

> 状态：v0.2（2026-11-17）
> 适用范围：`operator/` 下 22 个算子的模型调用、测试平替与本地权重管理
> 关联文档：[权重目录约定](权重目录约定.md)、[许可证清单](许可证清单.md)、[算子工程契约](算子工程契约.md)
> 验证脚本：[scripts/model_gateway_smoke.py](../../scripts/model_gateway_smoke.py)

## 1. 决策标准

1. **生产优先使用服务器模型**（内网模型网关）。
2. **测试阶段使用硅基流动（SiliconFlow）对应平替**；平替只用于联调，不得进入生产。
3. 同一能力有多个候选时，**在效果达标的前提下选最小模型**；效果优先于体积。
4. 服务器和测试平替都覆盖不到、且本地测试确实需要的模型，下载到 `D:\models`（Linux `/models`）。
5. 许可证未审批的模型不得进入镜像或生产（Q-07 / H-06）。

### 1.1 “效果达标”的口径

以下为联调阈值，最终以 H-03（阈值口径）/ H-05（人工标注）确认为准：

| 能力 | 对比基线 | 达标线 |
| --- | --- | --- |
| 文本向量/聚类 | 当前 `bge-base-zh-v1.5` | 簇一致性（ARI）与下游标签准确率下降 ≤ 2 个百分点 |
| 标签重排 | 不加重排的 topK 结果 | nDCG@5 提升 ≥ 2 个百分点才值得引入 |
| 图像/多模态打标 | 当前 OCR + CLIP base | 人工小样（≥200 条）一致率下降 ≤ 2 个百分点 |
| ASR | 当前 `paraformer-zh` | 中文测试集 CER 上升 ≤ 2 个百分点，且标点/VAD 不劣化 |
| NER/知识抽取 | 当前规则抽取 | 实体召回/准确率提升 ≥ 5 个百分点 |
| 安全判定 | 无基线（新增能力） | 抽检准确率 ≥ 95%，误杀率可接受 |
| LLM 仲裁/抽取 | 最大模型（32B 级） | 一致率 ≥ 95% 才允许降到 3B/9B |

## 4. 小模型优先与升级策略

1. **默认走小模型**：生产文本向量 `Qwen3-Embedding-0.6B`（服务器最小可用）、本地 `bge-base`；ASR `Qwen3-ASR-0.6B`/`paraformer`；安全 `Qwen3Guard-0.6B`；LLM `Qwen2.5-3B-Instruct`。
2. **只在以下条件升级**：
   - 文本向量：文档普遍超过 512 token，或非中文占比 > 20% → `bge-m3` / `Qwen3-Embedding-0.6B`；
   - 标签：kNN topK 置信度低于阈值或人工抽检不达标 → 加重排 → 仍不达标再用 9B/32B 仲裁；
   - 图像：OCR/CLIP 置信度低 → VLM 兜底；
   - 知识：GLiNER 漏抽 → 3B 抽取 → 仍不足再上 32B。
3. **升级必须留痕**：在算子 metrics 中记录实际模型名、升级原因、升级比例；升级比例长期 > 20% 说明小模型不达标，应重新选型而不是无脑升级。
4. **降维/换维是破坏性变更**：768 → 1024 维会改变 OP-03 向量、OP-05/06 阈值与 OP-20 索引，必须重跑下游并更新证据。

## 5. 服务器网关协议（磐智/IDG，已确认）

依据 `docs/参考记录/聊天记录.txt`、`docs/参考记录/qwen35_9b_call.py`、
`docs/参考记录/deployment-kit/03_IDG_MODEL_GATEWAY.md` 与 `model_gateway/idg_signing_example.py`：

1. **不是 OpenAI Bearer 认证**，是磐智签名头网关；请求体/响应体仍按 OpenAI 风格
   （chat 返回 `choices[0].message.content`，embedding 返回 `data[].embedding`）。
2. **模型按 PATH 路由**：`<gateway-base>/<model-path>`，如 `/Qwen3.5-9B`、
   `/Qwen3-Embedding-0.6B/embeddings`、`/data-produce-1`（即 qwen3.8-27B）。
   PATH 必须严格按服务方登记值使用，不改大小写、不自行拼写。
3. **签名头**（每次调用重新生成时间戳与随机数）：

   ```text
   csid           = APPID + capability.ljust(24, "0") + uuid4().hex
   X-Server-Param = base64(json({"appid": APPID, "csid": csid}))
   X-CurTime      = str(int(time.time()))
   X-CheckSum     = md5(APPKEY + X-CurTime + X-Server-Param)
   appKey         = APPKEY
   ```

   `capability` 默认取 PATH 首段（≤24 字符）；若平台为该路由单独登记了
   ASCII 能力名，用 `MODEL_CAPABILITY` 覆盖。
4. **响应校验**：响应头 `X-Code` 必须为空或 `1000000`；`X-IsSync` 不能为 `false`。
5. **凭据**：APPID/APPKEY 全模型共用（APPID=`audioasr`；APPKEY 由运维/平台提供，
   参考记录本地留存、不入库）。APPKEY 只从环境变量 `MODEL_APP_KEY` 注入，不写入代码与 git。
6. 网关地址形如 `http://<网关IP>:<端口>`（示例见 idg demo，如 `http://10.252.92.98:9050`），
   生产值由运维提供，经 `MODEL_GATEWAY_BASE_URL` 注入。

冒烟脚本已支持双后端：`python scripts/model_gateway_smoke.py --backend panzhi`
（需内网可达 + `MODEL_GATEWAY_BASE_URL`/`MODEL_APP_KEY`）；硅基流动后端默认内置测试密钥。

环境变量（已实现：`operator/model_gateway.py` + `docker-compose.yml` 透传，**启动时切换，不改代码、不重建镜像**）：

| 变量 | 作用 |

| `SILICONFLOW_API_KEY` | 硅基流动密钥（兼容旧名 `MODEL_GATEWAY_API_KEY`） |
| `WEIGHTS_DIR` | 本地权重根，默认自动探测 `D:\models` / `/models` |
| `DEVICE` | `auto` / `cpu` / `cuda` / `cuda:N` |

启动与切换命令（运维口径，2026-11-17 团队约定）：

```bash
python scripts/stage_weights.py                # 构建前暂存 shared/ 权重并校验 SHA256SUMS
```

- **可变项部署时注入**（docker compose 环境变量，或 K8s Deployment 的 `env`
  按 `- name: / value:` 格式依次添加）：`MODEL_GATEWAY_BASE_URL`、`MODEL_APP_KEY`、
  `SILICONFLOW_API_KEY`、`MODEL_BACKEND` 覆盖、`DEVICE`、`MAX_UPLOAD_BYTES`/`MAX_EXTRACT_BYTES`。
- **密钥类走 K8s Secret**（`secretKeyRef`），不写明文。
- K8s 部署模板：`deploy/k8s/op-data-mixing.yaml`（namespace `obu-ai-cloud`、
  harbor 镜像路径、NodePort、资源限额均已按算子池现状预填）。

> 团队同类约定（引用原文，属于图像/视频生成算子的变量名，与本服务无关，此处仅备查）：
> `IMAGE_GEN_BACKEND=siliconflow VIDEO_PROVIDER=siliconflow SILICONFLOW_API_KEY=sk-xxx docker compose up -d`
> 切回 `IMAGE_GEN_BACKEND=idg VIDEO_PROVIDER=idg docker compose up -d`。
> 数据配比服务的等价开关是 `MODEL_BACKEND`。

`GET /health`（聚合探针）返回 `modelBackend`：当前后端、凭据是否就绪、缺失的
环境变量名（不回显密钥值），用于部署后确认切换是否生效。

安全约束：

1. `MODEL_BACKEND=idg` 时走磐智签名头与内网网关；密钥一律启动时注入。
2. 磐智 APPKEY 与硅基流动密钥**均不内置**在代码、配置或镜像中（2026-11-17 起撤销“冒烟脚本内置默认密钥”的做法）；签名时间戳与随机数每次调用重新生成。
3. 模型升级/降级必须在 metrics 中记录逻辑名、实际模型 ID 与原因。
