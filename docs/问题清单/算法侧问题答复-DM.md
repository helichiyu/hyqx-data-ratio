## 1. 权重交付（对应问题清单第 1 条、第 5 条）

### 1.1 现状

权重已经放进算子目录，和镜像构建上下文一致：

```text
operator/weights/shared/
├── bge-base-zh-v1.5/     # 391 MB，文本/标签向量，OP-03/05/06/20 共用
├── paraformer-zh/        # 953 MB，中文 ASR，OP-05/11 共用
├── fsmn-vad/             # 3.9 MB，语音端点检测
└── ct-punc/              # 283 MB，标点恢复
```

2026-11-19 执行 `sha256sum -c SHA256SUMS`，全部文件校验通过。清单文件本身进 git，权重文件按约定不进 git。

图像文字识别使用的 RapidOCR 模型随 `rapidocr-onnxruntime` wheel 打包，不需要额外权重文件。因此覆盖文本、图像、音频、视频四类打标，只需要上面四套共享权重，另加 ffmpeg 做音视频解码。

### 1.2 交付方式与注意事项

`operator/.dockerignore` 已允许 `weights/` 进入构建上下文，`Dockerfile` 在构建期按 `SHA256SUMS` 逐项校验，校验失败即构建失败；镜像运行期不联网下载。

需要注意：`.gitignore` 排除了 `operator/weights/**`。因此

- 用目录打包、tar、或者构建镜像的方式交付，权重会被一起带走；
- 用 `git clone` 的方式交付，权重不会被带走，需要在目标机执行 `python scripts/stage_weights.py`，或单独拷贝 `weights/`。

### 1.3 目录约定

解析顺序是 `WEIGHTS_DIR` 环境变量、本机模型仓（Windows `D:\models`、Linux `/models`，需含 `shared/`）、镜像内 `operator/weights/`。生产镜像不依赖模型仓，`operator/weights/` 必须完整。

## 2. 语音算子运行环境（对应问题清单第 2 条）

### 2.1 是否支持 CPU

支持。`dm-speech-analysis` 使用 FunASR `paraformer-zh`，CPU 可推理，不要求 GPU，也没有最低显存要求。GPU 是可选项，不是前置条件。

GPU 场景的约束由镜像固定：torch 为 2.6.0 的 cu124 构建，构建期校验 CUDA runtime 不超过 12.4；生产驱动 12.4 可直接使用，12.8 驱动向后兼容。镜像不安装 CUDA toolkit，宿主机只需满足驱动版本并安装 nvidia-container-toolkit。

### 2.2 依赖版本

`operator/requirements.txt` 已锁定，生产镜像、本地复现都应以它为准：

| 依赖 | 版本 |
| --- | --- |
| torch | 2.6.0（PyPI 默认 cu124 wheel） |
| transformers | 4.43.4 |
| funasr | 1.4.16 |
| modelscope | 1.40.1 |
| librosa | 1.0.0 |
| soundfile | 0.14.0 |
| onnxruntime | 1.32.0 |

本地建环境请直接执行 `pip install -r operator/requirements.txt`。`docs/联调部署/联调步骤-DM.md` 原来那份手写 pip 清单漏掉了 torch、transformers、funasr 等依赖，照那份装必然出现“缺 torch”，已修正为按 requirements 安装。

### 2.3 ffmpeg

音频/视频解码、关键帧提取、长音频切片都依赖 ffmpeg。生产 `Dockerfile` 已安装；本机联调需要自行安装（apt、conda 或官方构建均可），否则 `/{operatorId}/healthz` 的 `dependencyStatus.ffmpeg` 会显示 missing。

单条音频超过 5 分钟会切片转写，超过 30 分钟直接返回 `ASR_FAILED` 并提示平台分片；这是算子边界，不是环境问题。

## 3. 模型网关（对应问题清单第 4 条）

当前 14 个算子没有任何一个调用模型网关：代码里没有网关 HTTP 调用，也没有把网关客户端引入算子 core。`/health` 的 `modelBackend` 只是探针展示，凭据缺失时显示 `credentialsOk=false`，不影响打标、画像、仿真、生产、分析任何任务。

因此：

- 联调阶段不需要为了跑通任务注入网关凭据；
- 如果平台要求健康检查全绿，联调环境给 `MODEL_BACKEND=siliconflow` 和 `SILICONFLOW_API_KEY` 即可；
- 生产如果启用 idg 网关，`MODEL_GATEWAY_BASE_URL`、`MODEL_APP_KEY` 由部署时以环境变量或 Secret 注入，不进代码、不进镜像；`MODEL_BACKEND`、`MODEL_APP_ID`、`SILICONFLOW_BASE_URL` 是镜像内固定默认值；
- 后续新增依赖大模型的算子，会在算子 README 和健康检查里明确声明，不会隐式依赖。

## 4. 打标结果契约（对应问题清单第 6 条）

### 4.1 labels 顺序与主标签

分类命中时，`labels` 数组当前只有一条，就是主标签；`topK` 按相似度降序排列，置信度是 topK 内 softmax 的结果。平台取 `labels[0]`、并把 `topK` 原样落库，口径正确。

### 4.2 路径分隔符

`labels[].path` 输出的是数组，例如 `["社会与群体", "群体与活动", "职业形象"]`。平台用 `/` 拼接成 `labelPath`，与分类树 `node_path` 的 `/` 分隔完全一致，不存在分隔符冲突。

### 4.3 未归类样本

未归类记录仍然保留在 `result.jsonl` 中，字段为 `labels=[]`、`unclassified=true` 并带 `reasonCode`；同时另写 `unclassified.jsonl`。工具类失败（OCR、ASR、关键帧、媒体缺失）写入 `failures.jsonl`，并在 `result.jsonl` 保留一条 `labels=[]` 记录，便于对账。

实际的原因码是 `UNCLASSIFIED_LOW_SIMILARITY`、`UNCLASSIFIED_LOW_CONFIDENCE`、`UNCLASSIFIED_SMALL_MARGIN`、`UNCLASSIFIED_NO_TEXT_EVIDENCE`、`UNCLASSIFIED_NO_SPEECH` 这一类带前缀的值。OP-05 README 原来写成短名，已修正。

### 4.4 treeVersion

当前 OP-05/OP-06 使用镜像内的固定树快照，版本为 `taxonomy-1013-pending`，并在结果和 manifest 中回写该版本。平台请求里的 `treeVersion` 目前没有传给算子，详见第 5 节。

## 5. 分类树版本（对应问题清单第 6 条第 3 问）

### 5.1 现状

平台前端可以修改分类树：新增、改名、删除、启停、排序节点，以及创建版本快照、切换生效版本。当前实现里，**生效版本的节点可以直接改**，`treeVersion` 字符串不会随内容变化，因此只靠版本号无法判断树内容是否变过。

算子侧目前只认镜像内的 `taxonomy-1013-pending` 快照，没有接收平台树的参数。两边不一致时，标注路径会与新树对不上，平台标签校验会按当前树校验并报“标签路径不在当前分类版本内”。

### 5.2 已实现方案：每次任务携带完整快照

不采用“算子容器记住修改”的方式：容器会重启、可能多副本、不同任务可能同时使用不同版本，进程内状态不可靠，也无法追溯。

现行实现改为每次任务携带完整树快照：

1. 平台侧新增 `TaxonomyService.snapshot(treeVersion)`，从数据库导出启用节点，结构为 `treeVersion` 加 `trees{content/domain/ability}.nodes`，节点路径为数组、`leaf` 为布尔值；
2. 打标任务启动时按任务的 `treeVersion` 生成快照，画像 basic 任务按当前生效版本生成快照；
3. 网关把快照 JSON 上传到算子池独立目录，并在 `predict` 参数里传 `tree_snapshot_path` 与 `tree_version`；
4. OP-05、OP-06、OP-08 只在本 run 内读取该快照，不修改镜像内基线；结果、metrics、manifest 回写 `treeVersion`、`treeHash`、`treeSnapshotPath`；
5. 快照没传时回落到镜像内默认树，结果里如实标注默认版本；
6. `tree_version` 与快照内版本不一致时直接失败，不允许静默串版本。

快照通常只有几百 KB，比差异协议简单，且多副本、重启、并发、重试都没有状态问题，历史任务能按当时的版本和哈希复现。

平台侧两件收尾事项已经改成代码约束：

1. 生效版本不允许直接增删改节点、启停或排序，必须先用“创建版本”生成草稿，编辑完再切换生效；这样 `treeVersion` 与内容始终对应，不会再出现同版本号内容漂移。根节点新增时可以指定 `versionId` 指向草稿版本。
2. 节点改名或移动时，同步迁移 `hs_data_mixing_sample_label` 的标签路径与标签名称，避免历史引用失效。删除节点仍保留“被样本标签引用时拒绝删除”的保护。专家校验已删除，不再维护专家样本路径。

## 6. 置信度阈值（对应问题清单第 7 条）

平台默认值已从 0.6 改为 0.25（`DmThresholdProperties.labelConfidence` 与 `application.yml` 的 `label-confidence`），新建打标任务在不显式传值时使用 0.25，与 OP-05 默认值一致。阈值版本同步从 `dm-2026-11-18` 升到 `dm-2026-11-19`，新任务与结果快照会记录新版本，历史结果仍可按旧版本追溯。

依据：用现有 425 条文本的打标证据统计，已标样本置信度中位数约 0.40，278 条已标样本中只有 23 条达到 0.6。按 0.6 放行会让约九成已标样本变成“低置信未归类”，后续生产选样会被抽空。

如果业务上确实需要 0.6，建议把它定义为“人工复核阈值”，与“自动打标下限”分开存两个字段；不要用同一个值同时承担两个语义。

## 7. 领域覆盖与 OP-06（对应问题清单第 3 条）

OP-08 的领域覆盖依赖 OP-06 的输出，且是**可选**输入：不传 `domain_labels_path` 时返回 `domainCoverage.status=unavailable` 和 `DOMAIN_LABELS_UNAVAILABLE`，不推测分布。

平台画像链已经改为 OP-01 → OP-02 → OP-06 → OP-08：basic 画像在标准化之后先调 `dm-taxonomy-labeling`，把 OP-06 的结果目录作为 `domain_labels_path` 传给 OP-08，链路里记录 `taxonomyDir` 和 `taxonomyRunId`，画像结果备注里也会保留这两个值。

失败策略按“不允许失败”执行：OP-06 失败会让整个 basic 画像任务明确失败并带原因码，不做静默降级。配置好权重和依赖是前置条件，出问题就按错误信息修，而不是让领域覆盖悄悄变成不可用。

GPU 与超时：算法网关把 `device` 参数透传给 OP-06 和 OP-05，默认 `auto`（有 GPU 用 GPU，没有回落 CPU），GPU 节点可用 `DM_ALGORITHM_DEVICE=cuda` 强制；单次 predict 和任务总超时从 30 分钟放宽到 2 小时，避免大样本向量计算被截断。

分类树快照已经可以在调用时传入，OP-06 和 OP-08 用同一份快照即可保证路径口径一致；权重也已就位。

另外，`operator/map.json` 里 OP-06 登记了依赖 OP-05、OP-08 登记了依赖 OP-05，与实际消费不符（OP-06 只读 OP-02，OP-08 只可选读 OP-06）。这条登记会误导编排，建议修正，见 `docs/算子开发/算子编排与依赖说明.md`。

## 8. 人工标注与准确率（本轮新增口径）

### 8.1 准确率、F1、混淆矩阵是什么

这三个都是“拿预测结果和标准答案逐条比对”得到的指标。标准答案就是人工或权威标注给出的正确标签，比如这条文本实际属于“教育/教学与培训/K12教育”。

准确率是判对的条数除以总条数，回答“整体有多少比例判对了”。

精确率和召回率是分类问题里更细的两个口径：精确率回答“判成这个标签的样本里有多少是真的”，召回率回答“真正属于这个标签的样本里有多少被找出来”。F1 是精确率和召回率的调和平均，用一个数同时兼顾两者，适合类别不均衡或多标签场景。

混淆矩阵是一张“真实标签乘预测标签”的计数表，能看出哪个标签经常被误判成哪个标签，比如把“时政新闻”判成“社会新闻”的有多少条。

### 8.2 为什么没有标准答案就算不出来

没有标准答案时，唯一能确定的是模型自己输出了什么，没法判断对错。此时能算的只有标注率、置信度分布、路径合法率、证据完整度、跨模型一致性这类过程指标；它们能说明“标了多少、敢不敢信、路径是否合法”，但不能说明“标得对不对”。把过程指标叫成准确率就是伪造评测结论。

按 FGW 原文，真正提到分类精度评估的只有一处：文本体裁分析要求“基于微调模型区分新闻、论文、对话等多类体裁，使用混淆矩阵评估分类精度”。任务书里 OP-05 的准确率/Wilson、OP-18 的宏 F1、OP-21 的 Kappa/P-R-F1，都是我们自己生成的任务书条款，不是 FGW 原文要求；其中 OP-18、OP-21 已经随本次范围调整删除，不再作为验收项。

任务书自己也写了“禁止编造指标：没有人工标注/真值时不填准确率、F1、Kappa；写 null + blockedReason”。因此当前实现不计算这些指标，也没有任何页面或流程把它们当门槛。OP-05、OP-06 已删除 accuracy/Wilson/混淆矩阵字段，只保留标注率、置信度分布、路径合法率等过程指标；平台侧专家校验页面与 Kappa/准确率计算也已删除。

### 8.3 平台上没有强制人工卡点

核对后端流程后确认：

- 打标任务完成后即 `completed`，复核状态只是统计字段，不阻塞完成；
- 配比生产只要求存在“已完成的打标任务”，不要求复核通过；
- 配比分析、报告不依赖任何人工复核；
- 专家校验已按 Comic 任务书删除，页面与接口不再提供；
- 评测类字段为空时不影响任何任务完成。

因此当前没有任何“必须人工标注才能继续”的强制卡点。如果后续前端增加了这类卡点，应当去掉或改为可跳过。

### 8.4 可选的小样本校准

如果需要一个可信度参考，可以由算法侧自行标注一小批样本（建议 100 到 200 条，覆盖文本、图像、音频、视频各若干），只用于离线校准阈值和抽查，不进入平台任务流，不作为页面卡点。

如果要大范围准确率（比如每个模态上千条、或要求统计显著），需要单独的标注流程、标注规范和人力，这需要双方先讨论，不能靠算子自行生成标注。

### 8.5 FGW 体裁混淆矩阵的解决思路

FGW 这句要求的是“体裁分类能力可评估”，不是要求每条业务数据都带真值。可以按模型级离线评估来做：

1. 建一个小型体裁金标集，建议 8 类体裁各 30 条左右，共约 240 条，来源用公开语料或已有授权样本，由我们人工确认标签。这个集合独立于客户数据，不要求客户提供标注。
2. 体裁分类从关键词规则升级为模型方法：用 bge 向量加一个线性分类头，在金标集上按训练/验证划分；样本太少时先用零样本原型分类，后续再补微调。
3. 写离线评估脚本，输出准确率、宏 F1、逐类精确率/召回率、混淆矩阵和错标清单，证据落在 OP-10 的 output/evidence 下，作为 FGW 要求的评估材料。
4. OP-10 增加可选的 `truth_path` 参数：传了真值就按批次算混淆矩阵；没传时正常产出体裁分布，并把模型级金标评估作为参考，数据集级准确率仍标 null，不伪造。
5. 这套评估只在离线做一次或按模型版本更新，不进入平台任务流，也不做页面卡点。

这样既满足 FGW 的“混淆矩阵评估分类精度”，又不需要客户数据带标准答案。金标集二百多条，属于此前你允许的“小批量自己标注”范围；如果要做统计显著的分体裁报告，再讨论扩大标注。
